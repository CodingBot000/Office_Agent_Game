# 증거 제시 및 대상별 NPC 반응 개발계획서

## 1. 문서 목적

QA에게 확보한 증거를 다른 NPC에게 제시했을 때, 대상 NPC의 역할·성격·현재 상태에 맞는 반응이 나오도록 백엔드, Unity 클라이언트, 웹 프론트엔드를 확장한다.

핵심 방향은 혼합형이다.

- 게임 규칙, 증거 유효성, 관계 수치 변화는 백엔드가 고정 규칙으로 통제한다.
- NPC가 실제로 말하는 문장은 AI provider가 현재 NPC 상태와 증거 내용을 바탕으로 생성한다.
- AI 응답은 백엔드 guardrail과 허용된 결과 범위 안에서만 적용한다.

## 2. 현재 상태 및 문제

현재 백엔드는 qa_warning_message 같은 증거를 세션의 discovered_evidence에 저장하고, show_evidence intent를 처리할 수 있다.

현재 문제는 다음과 같다.

- Backend Developer에게 QA 경고를 제시하는 경우에만 별도 반응이 있다.
- QA, Frontend Developer, PM에게 제시하면 공통 메시지만 출력된다.
- 대상 NPC의 성격과 관계 상태에 따른 증거 반응 정책이 부족하다.
- Unity와 웹은 증거 확보·제시 결과를 표시하지만, 대상별 반응의 의미가 충분히 드러나지 않는다.

## 2-1. 정보 공개 단계 및 대화 공개 정책

NPC가 알고 있는 정보와 현재 대화에서 공개할 수 있는 정보는 분리한다.

### 일반 대화

인사, 현재 상태, 진행 상황, 무엇을 확인 중인지 묻는 질문에는 증거 원문이나 정확한 에러명을 공개하지 않는다.

허용 예시:

- 배포 전 검증 로그와 API 응답을 대조하고 있습니다.
- QA 테스트 결과를 확인하고 있습니다.
- 정확한 내용은 증거를 정리한 뒤 공유하겠습니다.

단, 플레이어가 이미 확보해 화면에 표시된 증거를 가리키며 “이게 뭐야?”, “이 내용은 무슨 뜻이야?”처럼 후속 질문을 하면 같은 증거를 다시 요청하게 하지 않고 해당 증거의 의미를 설명한다.

### 명시적 증거 요청

다음과 같이 구체적인 공개를 요청한 경우에만 증거 확보 또는 제시 흐름을 실행한다.

- 정확한 에러명이 무엇인지 알려줘
- 에러 메시지를 보여줘
- QA 경고 원문을 공개해줘
- 구체적인 이슈 내용을 설명해줘
- 확보한 증거를 Backend Developer에게 제시해줘

### 컨텍스트 보호

- talk와 일반 ask에는 증거 본문을 AI 컨텍스트로 전달하지 않는다.
- 일반 대화의 최근 이벤트에는 증거가 확보되었다는 사실과 제목만 포함할 수 있다.
- request_evidence와 show_evidence에서만 백엔드가 증거 본문을 전달한다.
- AI가 일반 대화에서 증거 원문을 반환하면 deterministic 안전 응답으로 대체한다.

### 대상 일관성

Unity 또는 웹에서 선택한 NPC는 대화·질문·증거 제시의 기본 대상이 된다. AI가 임의로 다른 NPC를 선택하지 않도록 백엔드가 target hint를 검증하고 강제한다.

### 책임자·담당자 라우팅

플레이어가 “이 일의 책임자나 담당자가 누구인지”, “누구에게 물어봐야 하는지”를 질문하면 NPC가 단순히 모른다고 답하지 않도록 한다.

책임 범위는 다음처럼 분리한다.

- 실제 Production 배포 실행: Backend Developer
- API 계약·응답 스키마 변경: Backend Developer
- 릴리스 일정 단축과 일정 압박: PM / Planner
- 배포 전 품질 검증과 차단 경고: QA Engineer
- 최종 승인 확인 누락: 실제 NPC가 아닌 배경 사건 사실

QA는 배포 권한이 없다고만 답하지 않고 Backend Developer와 PM을 각각 안내한다. PM도 기술 세부사항은 Backend Developer에게, 일정과 압박 경위는 본인이 설명할 수 있다고 안내한다. Team Lead는 실제 대화 대상이 아니므로 플레이어에게 찾거나 연락하라고 안내하지 않는다. 책임자 질문은 서버가 소유한 역할 라우팅으로 처리해 AI provider가 담당자를 모른다고 답하는 것을 차단한다.

## 3. 목표 사용자 흐름

### 증거 확보

1. 플레이어가 QA에게 경고 메시지 또는 에러 증거를 요청한다.
2. 백엔드가 증거를 discovered 상태로 변경한다.
3. 모든 클라이언트에 '증거를 확보했습니다.' 이벤트가 표시된다.
4. 증거 목록에 확보된 증거의 제목과 본문이 표시된다.

### 증거 제시

1. 플레이어가 증거 목록에서 증거를 선택한다.
2. 현재 대화 대상에게 '증거 제시하기'를 실행한다.
3. 백엔드가 대상 NPC, 증거 출처, NPC 상태, 관계 상태를 검증한다.
4. 대상 NPC의 반응 메시지와 관계·상태 변화를 적용한다.
5. 클라이언트에 다음 정보를 표시한다.
   - 플레이어가 증거를 제시했다는 이벤트
   - 제시한 증거 본문
   - 대상 NPC의 반응
   - 변경된 신뢰도·긴장도·감정 등

## 4. 증거 제시 정책

### 공통 검증 규칙

- 증거가 세션에 존재해야 한다.
- 플레이어가 해당 증거를 먼저 확보해야 한다.
- 대상 NPC가 현재 세션에 존재해야 한다.
- 이미 제시한 증거를 다시 제시할 수는 있지만, 중복 제시에는 별도 반복 반응 정책을 적용한다.
- 증거 본문은 백엔드가 소유하며 AI가 임의로 변경할 수 없다.

### 대상별 반응 방향

반응 방향과 상태 변화는 고정하고, 실제 문장 표현은 AI가 생성한다.

| 대상 | 증거 출처 | 기본 반응 방향 | 기본 상태 변화 |
|---|---|---|---|
| QA Engineer | QA | 자신이 보낸 증거임을 확인하고 경고가 무시된 경위를 설명 | 신뢰 소폭 증가 또는 유지 |
| Backend Developer | QA | 경고를 알고도 배포했는지 설명하거나 책임을 인정 | 긴장·스트레스 증가, 상황에 따라 신뢰 감소 |
| Frontend Developer | QA | API 변경과 QA 경고의 연관성을 검토 | 협조도 또는 긴장도 변화 |
| PM / Planner | QA | 일정 압박과 승인 과정의 책임을 검토 | 긴장도 증가, 증거 기반 대화 가능 |

### 동일 출처 재제시

QA에게 QA가 작성한 증거를 다시 제시하는 경우에는 무반응으로 처리하지 않는다.

예시 방향:

> 이 메시지는 제가 보낸 경고입니다. 이미 알고 있는 내용이니, 이 경고가 어떻게 처리됐는지 확인해 주세요.

이 경우 동일 증거의 신규 확보나 중복 보상은 발생하지 않고, already_known_evidence 반응 유형을 기록한다.

### 반복 제시

같은 증거를 같은 NPC에게 반복해서 제시할 경우:

- 첫 제시: 기본 반응 및 관계 변화
- 두 번째 제시: 반복 제시 경고 또는 반응 강도 감소
- 세 번째 이후: '이미 확인한 증거입니다.'와 함께 추가 수치 변화 없음

## 5. 백엔드 설계

### 증거 반응 정책 모듈

기존 _show_evidence() 내부에 모든 분기를 직접 추가하지 않고, 별도 정책 함수 또는 모듈로 분리한다.

권장 구성:

~~~text
EvidencePresentationPolicy
├── validate_presentation()
├── resolve_reaction_type()
├── calculate_state_changes()
└── build_reaction_context()
~~~

### 반응 유형

~~~text
first_presentation
same_source_acknowledgement
cross_role_review
accountability_pressure
repeated_presentation
invalid_presentation
~~~

### AI provider 입력 컨텍스트

AI에게 다음 정보를 제공한다.

- 증거 ID, 제목, 본문, 출처 NPC
- 대상 NPC ID, 역할, 성격
- 대상 NPC의 감정·스트레스·신뢰도·협조도
- 플레이어와의 관계 수치
- 이전에 같은 증거를 제시했는지
- 고정된 반응 유형
- 허용된 상태 변화 범위

AI가 반환할 수 있는 결과는 구조화된 스키마로 제한한다.

~~~json
{
  "reaction_type": "accountability_pressure",
  "dialogue": "QA 경고가 있었던 것은 확인했습니다. 당시 배포 판단 과정을 다시 검토하겠습니다.",
  "emotion": "uneasy",
  "stress_delta": 5,
  "trust_delta": -2,
  "cooperation_delta": 3,
  "memory_candidate": "QA 경고 메시지가 배포 전에 제시되었다."
}
~~~

백엔드는 AI가 반환한 값이 정책 범위를 벗어나면 deterministic fallback을 사용한다.

### 시나리오 사실 일관성 guardrail

증거 제시 반응의 문장도 서버가 보유한 canonical fact를 부정할 수 없다.
특히 Backend Developer의 QA 경고 제시 반응에서는 다음 사실을 유지한다.

- Backend Developer가 실제로 릴리스를 배포했다.
- Backend Developer가 API 응답 스키마를 변경했다.
- QA 경고가 배포 전에 전달되었다.

AI가 “배포하지 않았다”처럼 해당 사실을 명시적으로 부정하면 서버는 해당 문장을 적용하지 않고 deterministic 반응으로 대체한다.
“검증 전에 배포하지 않았어야 했다”처럼 과거 판단에 대한 후회·책임 인정 표현은 사실 부정이 아니므로 허용한다.

### 응답 및 이벤트

증거 제시 응답은 기존 message 외에 필요하면 다음 필드를 확장한다.

~~~json
{
  "classified_action": "show_evidence",
  "evidence_id": "qa_warning_message",
  "target_id": "backend_01",
  "reaction_type": "accountability_pressure",
  "message": "증거를 제시했습니다.",
  "evidence_content": "[16:40] QA: Critical ...",
  "recipient_reaction": "QA 경고가 있었던 것은 확인했습니다.",
  "state_changes": {
    "trust_delta": -2,
    "stress_delta": 5,
    "cooperation_delta": 3
  }
}
~~~

기존 클라이언트와의 호환성을 위해 기존 message, alert, snapshot 필드는 유지한다.

## 6. Unity 반영 계획

### 증거 목록

- I 정보 패널에 증거 탭을 제공한다.
- 전체 증거 수와 확보 증거 수를 표시한다.
- 미확보 증거는 제목과 요약만 표시한다.
- 확보 증거는 제목과 본문을 표시한다.

### 자동 확보 메시지

- 새 증거가 발견된 snapshot을 받으면 한 번만 대화 기록에 추가한다.
- 메시지는 빨간색으로 표시한다.
- 같은 snapshot이 반복 수신되어도 중복 표시하지 않는다.

### 증거 제시 버튼

- 현재 대화 대상이 있고 확보된 증거가 있으면 대화창에 버튼을 표시한다.
- 증거별로 증거 제시하기 버튼을 만든다.
- 버튼 실행 후 입력창은 잠시 잠그고 응답을 기다린다.
- 플레이어 이벤트, 증거 본문, 대상 NPC 반응을 순서대로 표시한다.

### Unity 데이터 모델

OfficeSnapshotDto에 다음 정보를 포함한다.

- evidences
- id
- title
- summary
- content
- source_npc_id
- discovered

## 7. 웹 프론트엔드 반영 계획

### 증거 목록

- NPC Inspector의 Evidence 영역에서 확보 여부를 표시한다.
- 확보된 증거는 본문을 보여준다.
- 미확보 증거는 요약만 보여준다.

### 증거 제시 영역

- 자연어 입력창 위에 DISCOVERED EVIDENCE 영역을 표시한다.
- 현재 선택된 NPC를 대상 NPC로 표시한다.
- 확보된 증거별 증거 제시하기 버튼을 제공한다.
- 제출 중에는 버튼을 비활성화한다.

### 이벤트 시각화

- event_type=evidence인 이벤트는 빨간색으로 표시한다.
- 확보 메시지, 증거 본문, 제시 완료, 대상 NPC 반응을 한 이벤트 흐름으로 보여준다.

## 8. 테스트 계획

### 백엔드 테스트

- QA 증거 요청 시 discovered=true가 되는지 확인
- 확보하지 않은 증거 제시가 차단되는지 확인
- QA에게 자기 증거를 제시했을 때 same_source_acknowledgement가 나오는지 확인
- Backend에게 QA 경고를 제시했을 때 배포 실행 사실을 부정하는 AI 응답이 deterministic fallback으로 대체되는지 확인
- QA에게 책임자를 물었을 때 Backend Developer와 PM을 담당 영역별로 안내하는지 확인
- PM에게 책임자를 물었을 때 Backend Developer의 배포·API 담당과 PM의 일정 담당을 구분하는지 확인
- 책임자 질문이 단순 `모르겠습니다` 응답으로 끝나지 않는지 확인
- 실제 NPC가 아닌 Team Lead를 찾아가라는 안내가 fallback으로 대체되는지 확인
- Backend Developer에게 QA 증거 제시 시 책임 반응이 나오는지 확인
- Frontend Developer와 PM에게 각각 다른 반응 방향이 적용되는지 확인
- 동일 증거 반복 제시 시 상태 변화가 중복되지 않는지 확인
- AI 응답이 정책 범위를 벗어날 때 fallback이 적용되는지 확인

### Unity 테스트

- 증거 목록 탭에 확보·미확보 상태가 표시되는지 확인
- 증거 확보 이벤트가 한 번만 표시되는지 확인
- 대화 대상에 맞는 증거 제시 버튼이 표시되는지 확인
- 증거 제시 후 증거 본문과 NPC 반응이 표시되는지 확인
- 긴 증거 본문이 대화 스크롤 영역에서 잘리지 않는지 확인

### 웹 테스트

- 증거 확보 이벤트가 빨간색으로 표시되는지 확인
- 확보 후 제시 버튼이 나타나는지 확인
- 대상 NPC 변경 시 버튼의 대상명이 바뀌는지 확인
- 제시 중 중복 클릭이 차단되는지 확인
- 증거 제시 후 대상 NPC 반응과 상태 변화가 갱신되는지 확인

## 9. 구현 순서

1. 백엔드 증거 제시 정책과 반응 스키마 정의
2. 백엔드 대상별 deterministic fallback 구현
3. AI provider용 증거 제시 컨텍스트와 출력 스키마 추가
4. 백엔드 테스트 작성 및 기존 테스트 회귀 확인
5. Unity 증거 목록과 자동 확보 메시지 구현
6. Unity 증거 제시 버튼과 반응 표시 구현
7. 웹 증거 제시 영역과 이벤트 스타일 구현
8. Unity·웹 통합 테스트
9. 로컬 백엔드와 원격 백엔드에서 동작 확인

## 10. 완료 기준

- 모든 대상 NPC가 증거 제시에 대해 최소 하나의 의미 있는 반응을 반환한다.
- 대상별 반응 방향과 관계 수치 변화가 정책에 의해 제한된다.
- AI provider가 실패해도 deterministic 반응이 표시된다.
- 증거 확보 메시지와 증거 본문이 중복되지 않는다.
- Unity와 웹에서 증거 확보·목록 표시·제시·반응 확인이 동일한 상태를 반영한다.
- 기존 대화, 이동, 물품 액션, 최종 보고서 기능에 회귀가 없다.
